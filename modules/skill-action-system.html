Skill / Action System

Skill System은 입력이나 AI 의도를 비용, 쿨다운, 타겟팅, 액션 타임라인, EffectBundle 실행으로 변환하는 조율 계층이다. C# 참조는 불변 요청·결과뿐 아니라 SkillAdmissionPolicy와 FireballSkillPlanner로 대상 생존 → cooldown → resource 우선순위, readyTick <= RequestedTick, snapshot version plan과 stale rollback을 실행 검증한다. 예약·애니메이션 timeline은 여전히 개념 확장이다.

Skill System의 책임 경계

Skill은 HP를 직접 깎지 않는다. Skill은 입력과 행동 조건을 검증하고, 적절한 타이밍에 EffectBundle 실행을 요청한다. DamageEffect가 필요하면 Effect System이 CombatResolver에 DamageRequest를 전달한다.

대상 지정 방식, 사거리, 시야, 무기 조건 검증 AI가 어떤 스킬을 선택할지 판단

Skill과 Effect의 차이

Skill은 “사용할 수 있는 행동”이고 Effect는 “적용되는 결과”다. 이 예제의 Fireball은 비용, 쿨다운, 단일 대상, release marker를 가지며 다른 스킬은 시전·차지·채널링 타임라인을 가질 수 있다. Fireball의 DamageEffect와 ApplyStatusEffect(effect.apply-burn)는 실제 대상에게 피해와 상태를 요청한다.

주의. 스킬마다 피해 계산 코드를 직접 넣기 시작하면 Effect, Combat, Status, Log 구조가 무너진다. 스킬은 EffectBundle을 실행하는 쪽에 머물러야 한다.

기본 흐름

Input / AI → SkillRequest → Validate → Timeline → EffectBundle → SkillResult

핵심 객체

객체 표의 증거 범위. SkillRequest, SkillDecision, SkillResult, SkillAdmissionPolicy, FireballSkillPlanner는 현재 실행 C#이다. SkillDefinition, SkillRuntime, SkillExecution, SkillBook, CostPolicy, CooldownPolicy, TargetingSpec, ActionTimeline, 범용 SkillExecutor는 책임을 설명하는 product 모델이며 현재 저장소의 구현 타입이 아니다.
객체 책임
SkillDefinition 스킬의 정적 데이터. 비용, 쿨다운, 타겟팅, 태그, 타임라인, EffectBundle 참조를 가진다.
SkillRuntime 특정 Entity가 가진 스킬의 장기 availability 상태. 배운 레벨, 쿨다운, 차지, 런타임 오버라이드를 가진다. 한 번의 시전 상태는 SkillExecution이 소유한다.
SkillExecution 한 번의 cast/channel을 나타내는 실행 인스턴스. ExecutionId, Phase, ReservedCost, TargetSnapshot, CancellationToken을 가진다.
SkillBook Entity가 배운 스킬 목록과 레벨, 해금 상태, 장착 슬롯을 관리한다.
SkillRequest 스킬 사용 요청. CommandId, CasterId, SkillId, TargetId, RequestedTick, RootSeed를 포함한다. CommandId는 한 번의 cast와 commit 멱등성의 경계다.
SkillValidator 비용, 쿨다운, 상태 이상, 장비 조건, 사거리, 시야, 대상 유효성을 검증한다.
CostPolicy 비용을 언제 지불하고 언제 환불하는지 결정한다.
CooldownPolicy 쿨다운 시작 시점, 그룹 쿨다운, 차지 회복, 쿨다운 감소 적용 방식을 정의한다.
TargetingSpec 자기 자신, 단일 대상, 지점, 방향, 범위 미리보기 같은 입력 규칙을 정의한다.
ActionTimeline windup, cast, release marker, active frame, recovery, cancel window를 정의한다.
SkillExecutor 검증, 타임라인 진행, 비용·쿨다운 mutation과 EffectBundle plan 생성을 조율한다. 실제 상태와 outbox는 RuntimeCommitter가 확정한다.
SkillResult 성공/실패와 실행된 EffectResult 목록을 담는다. 실패 근거와 실행 단계는 연결된 DebugTrace에 남긴다.

C# 핵심 계약 · Executable abridged

SkillRequest는 한 번의 의도를 나타내는 불변 입력이고, SkillDecision은 실행 전 검증 결과, SkillResult는 실행이 끝난 뒤의 최종 결과다. 아래 코드는 학습에 필요한 불변식만 남긴 축약본이다. 예외 메시지와 전체 구현까지 포함한 규범 원본은 Contracts/Skills.cs이며, 실제 구현·복사에는 원본을 사용한다.

public enum SkillFailureReason
{
    NotLearned,
    OutOfResource,
    Cooldown,
    ControlLocked,
    InvalidTarget,
    Interrupted
}

public sealed class SkillRequest
{
    public EntityId CommandId { get; }
    public EntityId CasterId { get; }
    public EntityId SkillId { get; }
    public EntityId? TargetId { get; }
    public long RequestedTick { get; }
    public uint RootSeed { get; }

    public SkillRequest(
        EntityId commandId,
        EntityId casterId,
        EntityId skillId,
        EntityId? targetId,
        long requestedTick,
        uint rootSeed)
    {
        EntityId.ThrowIfInvalid(commandId, nameof(commandId));
        EntityId.ThrowIfInvalid(casterId, nameof(casterId));
        EntityId.ThrowIfInvalid(skillId, nameof(skillId));
        if (targetId.HasValue)
            EntityId.ThrowIfInvalid(targetId.Value, nameof(targetId));

        if (requestedTick < 0)
            throw new ArgumentOutOfRangeException(nameof(requestedTick));

        CommandId = commandId;
        CasterId = casterId;
        SkillId = skillId;
        TargetId = targetId;
        RequestedTick = requestedTick;
        RootSeed = rootSeed;
    }
}

public sealed class SkillDecision
{
    public SkillDecision(
        bool canExecute,
        SkillFailureReason? failureReason)
    {
        if (failureReason is { } reason && !Enum.IsDefined(reason))
            throw new ArgumentOutOfRangeException(nameof(failureReason));

        if (canExecute && failureReason is not null)
            throw new ArgumentException("Accepted request cannot have a failure reason.");

        if (!canExecute && failureReason is null)
            throw new ArgumentException("Rejected request requires a failure reason.");

        CanExecute = canExecute;
        FailureReason = failureReason;
    }

    public bool CanExecute { get; }
    public SkillFailureReason? FailureReason { get; }

    public static SkillDecision Accepted() => new(true, null);
    public static SkillDecision Rejected(SkillFailureReason reason) =>
        new(false, reason);
}

public interface ISkillRequestValidator
{
    SkillDecision Validate(SkillRequest request);
}

public sealed class SkillResult
{
    public bool Succeeded { get; }
    public SkillFailureReason? FailureReason { get; }
    public IReadOnlyList<EffectResult> Effects { get; }

    public SkillResult(
        bool succeeded,
        SkillFailureReason? failureReason,
        IEnumerable<EffectResult>? effects = null)
    {
        if (failureReason is { } reason && !Enum.IsDefined(reason))
            throw new ArgumentOutOfRangeException(nameof(failureReason));

        if (succeeded && failureReason is not null)
            throw new ArgumentException("Success cannot have a failure reason.");

        if (!succeeded && failureReason is null)
            throw new ArgumentException("Failure requires a reason.");

        EffectResult[] effectCopy =
            (effects ?? Enumerable.Empty<EffectResult>()).ToArray();
        if (effectCopy.Any(effect => effect is null))
            throw new ArgumentException("Effects cannot contain null.", nameof(effects));
        if (!succeeded && effectCopy.Length != 0)
            throw new ArgumentException("Failure cannot expose committed effects.", nameof(effects));

        Succeeded = succeeded;
        FailureReason = failureReason;
        Effects = Array.AsReadOnly(effectCopy);
    }
}

C# 실행 승인 정책과 snapshot plan

SkillAdmissionPolicy.cs는 살아 있는 명시적 대상 스킬의 작은 실행 정책이다. 한 요청에서 여러 조건이 동시에 실패해도 외부 실패 사유는 하나여야 하므로 대상 → cooldown → resource 순서를 계약으로 고정한다. FireballSkillPlanner.cs는 승인 뒤에만 Combat을 호출하고, resolve 때 읽은 mana·cooldown·shield·HP version을 commit precondition에 넣는다.

cast마다 새 실행 identity를 만든다. FireballReferenceScenario.cs의 FireballExecutionIdentity는 요청의 CommandId에서 SkillExecution Source, bundle/event/reaction ID, reaction 멱등 키와 정렬 키를 파생한다. 쿨다운 종료 tick은 RequestedTick + 60, DamageRequest seed는 해당 요청에 기록된 RootSeed를 사용한다. 같은 CommandId 재전송은 같은 cast의 멱등 replay이고, 반복 시전은 새 CommandId와 최신 tick·snapshot을 사용해야 별도 실행이 된다. RootSeed는 각 요청의 replay 입력으로 반드시 기록하되 전역 유일 ID는 아니다.
Snapshot결정부수 효과
targetHp == 0, cooldown·mana도 실패InvalidTargetCombat/RNG/plan 없음
readyTick > RequestedTick, mana도 부족CooldownCombat/RNG/plan 없음
readyTick == RequestedTick, mana 충분Acceptedresolve 후 versioned plan 생성
승인 뒤 Combat 결과가 MissAcceptedmana·cooldown만 mutation, Shield·HP 불변, zero-damage DamageCommitted, Burn reaction 없음
승인 뒤 cooldown version 변경commit의 PreconditionFailedmana·피해·outbox 모두 0
경계 의미. 쿨다운은 “현재 tick이 ready tick보다 크다”가 아니라 readyTick <= RequestedTick이면 준비된 것이다. 승인 정책은 snapshot을 바꾸지 않는 순수 함수이며, RNG와 Combat은 모든 deterministic guard가 통과한 뒤에만 실행한다.

목표형 실행기에서는 검증 뒤 Skill coordinator가 SkillExecution을 만들고 reserve_then_commit 정책이 release marker에서 비용·쿨다운·주 Effect의 commit plan을 준비한다. 현재 C#/JavaScript Fireball fixture는 예약·timeline·release 상태 머신을 구현하지 않고 검증 뒤 동등한 원자적 plan을 직접 만든다. 다른 CostPolicy의 확정 시점도 프로젝트 정책으로 별도 정의한다.

실행 파이프라인

증거 수준. 아래 ActionTimeline과 reserve_then_commit 예약 단계는 production 조율을 위한 Conceptual extension이다. 실행 참조는 불변 요청·결과, 대상/cooldown/resource 승인 순서, 승인 뒤 Combat 호출, snapshot version plan, 비용·쿨다운·주 Damage의 원자 commit과 stale rollback까지 검증한다.
  1. PlayerInput 또는 AI가 SkillRequest를 만든다.
  2. SkillDefinition과 SkillRuntime을 조회한다.
  3. 스킬을 배웠는지, 쿨다운 중인지, 비용이 충분한지, 침묵/기절/무장해제 상태인지 검증한다.
  4. TargetingSpec으로 사거리, 시야, 대상 타입, 지점 유효성을 검사한다.
  5. 비용을 예약하거나 정책에 따라 선지불한다.
  6. ActionTimeline을 시작하고 windup, cast, release marker, recovery를 진행한다.
  7. 목표형 reserve_then_commit 정책이면 release marker에서 비용·쿨다운 mutation과 EffectBundle의 주 효과를 하나의 CommitPlan으로 준비한다.
  8. RuntimeCommitter가 plan을 한 번에 commit한다. 성공하면 outbox의 SkillCommitted와 주 효과 이벤트를 발행하고, 그 이벤트로 만든 후속 반응은 ReactionQueue에 넣는다. 검증 실패는 SkillResult와 trace로 반환한다.

스킬 생명주기

SkillRuntime과 SkillExecution 분리

SkillRuntime은 배운 레벨, charge, cooldown처럼 오래 사는 availability 상태를 보관하고, SkillExecution은 cast 한 번의 임시 실행 상태를 보관한다. 둘을 합치면 동시 시전, 채널링, 취소, 서버 예측, 투사체가 남아 있는 상황을 안전하게 표현하기 어렵다. Ready/Cooldown과 Casting/Release/Recovery는 서로 다른 상태 축이며 구현에서는 별도 상태 머신으로 둔다.

Commit 직전 재검증. 요청 시점 검증만으로는 충분하지 않다. release marker에서 비용 예약, 대상 유효성, 제어 상태를 다시 확인하고 성공한 execution만 비용·쿨다운·주 효과를 하나의 commit plan으로 준비한다.

비용 정책

비용은 단순히 “사용 시 마나 감소”가 아니다. 시전형 스킬은 중단 가능성이 있으므로 지불 시점과 환불 정책을 명확히 해야 한다. Skill CostPolicy가 예약·확정 규칙을 소유하고, 실제 current resource 변경은 ResourceController가 atomic commit 안에서 수행한다. ModifyResourceEffect는 스킬 자체 비용이 아니라 회복·흡수 같은 게임 결과에 사용한다.

정책 설명 예시
on_request 입력 즉시 비용을 지불한다. 실패 여지가 적은 즉발 행동에 적합하다. 구르기, 즉발 회복
on_cast_start 시전 시작 시 비용을 지불한다. 가장 일반적인 방식이다. 짧은 채널링 회복 주문
on_release 판정 프레임에 도달했을 때 지불한다. 선딜 중 중단이 잦은 게임에 적합하다. 강한 차징 공격
reserve_then_commit 시작 시 비용을 예약하고 release에서 commit plan에 포함한다. 비용은 RuntimeCommitter의 commit 성공 receipt가 나온 뒤에만 최종 확정된다. Fireball, 네트워크 전투

쿨다운과 차지

쿨다운은 스킬 하나에만 붙는 값이 아니라 액션 시스템의 리듬을 만드는 규칙이다. 개별 쿨다운, 쿨다운 그룹, 글로벌 쿨다운, 차지 회복을 구분해야 한다.

Individual Cooldown

각 스킬이 독립적으로 재사용 대기 시간을 가진다. 단순하고 대부분의 액션 RPG에 적합하다.

Cooldown Group

같은 그룹의 스킬이 쿨다운을 공유한다. 물약, 회피기, 동일 무기 기술 묶음에 적합하다.

Global Cooldown

하나의 스킬 사용 후 짧은 공통 대기 시간을 둔다. 입력 폭주와 애니메이션 충돌을 막는다.

Charges

여러 번 연속 사용 가능한 스킬에 쓰인다. 각 charge의 회복 타이머와 쿨다운 감소 적용 방식을 정해야 한다.

Action Timeline

Diagram story · action timeline

Action Timeline을 세 실행 구간으로 읽기

입력 승인과 비용 정책, cast와 release 준비, atomic commit 이후를 분리한다. 애니메이션 시간과 게임 규칙의 commit 시점을 같은 것으로 보지 않는다.

3 DETAIL VIEWS

  1. Admission과 비용 시점

    SkillRequest를 먼저 검증하고 비용을 release까지 예약할지, 별도 prepay commit으로 먼저 지불할지 선택한다.

    • 검증 실패는 mutation과 event 없이 public failure로 끝난다.
    • reserve와 prepay는 중단 시 보상 규칙이 서로 다르다.

  2. Cast, interrupt, release preparation

    windup 중단 여부를 판단하고 release marker에 도달했을 때 Effect context와 plan을 준비해 Skill 변경과 합친다.

    • 중단은 예약 폐기 또는 명시적 prepay 보상으로 끝난다.
    • release marker가 EffectBundlePlan 준비의 게임 규칙 시점이다.

  3. Atomic commit과 post-commit 흐름

    결합된 plan을 한 번 검증·commit하고, 성공한 경우에만 committed fact, reaction, recovery 순서로 진행한다.

    • version 또는 invariant 실패는 모든 mutation과 outbox를 보존한다.
    • 후속 Burn 같은 반응은 이미 commit된 주 결과를 되감지 않는다.

EffectBundle 실행 정책

하나의 스킬은 여러 Effect를 묶을 수 있다. 이때 실행 정책은 “어디까지 한 번에 commit하고, commit 이후 반응을 언제 시작할지”를 정한다. Fireball의 기본 정책은 commit_then_react다. 비용·쿨다운·DamageEffect의 주 mutation과 outbox를 RuntimeCommitter가 원자적으로 commit한 뒤, 성공 receipt의 DamageCommitted fact만 ReactionQueue command로 바꿔 ApplyStatusEffect(effect.apply-burn)를 요청한다.

ExecutionPolicy commit 경계 reaction 실패 의미
commit_then_react 비용·쿨다운·주 Effect mutation과 outbox를 하나의 plan으로 검증하고 원자적으로 commit한다. 면역 정책을 추가한 확장에서 후속 Burn 반응이 실패해도 이미 commit된 피해는 유지한다. 현재 실행 fixture에는 Burn 면역 판정이 없다.

주 operation의 StopPolicy

StopPolicy는 주 operation 후보를 plan에 담는 방식을 정한다. commit이 끝난 작업을 되감는 정책이 아니며, 모든 검증과 선택은 상태를 바꾸기 전에 수행한다.

StopPolicy 선택 규칙 사용 예
all_or_nothing 주 operation 하나라도 검증 또는 precondition에 실패하면 plan 전체를 commit하지 않는다. Fireball의 비용·쿨다운·피해처럼 함께 확정되어야 하는 변경
best_effort_per_target 대상별 독립 command와 plan을 만들고, 한 대상의 실패가 다른 대상의 성공을 지우지 않게 한다. 광역 버프·디버프
stop_on_first_success 안정적으로 정렬한 후보를 검사해 처음 실행 가능한 대상 하나만 주 plan에 포함한다. 우선순위 기반 자동 대상 효과

  1. 정적 Definition data

    SkillDefinition이 비용·쿨다운·타깃·타임라인 정책과 EffectBundle 참조를 소유한다. 플레이 도중 변하는 값은 포함하지 않는다.

    • EffectBundleRef는 공개 Effect plan으로 이어지는 참조다.

    공개 요청을 validator가 판정하고, accepted인 경우에만 한 실행을 나타내는 SkillExecution이 만들어진다.

    • ReleasePlan은 상태 변경 전의 내부 준비물이다.
    • CommitReceipt는 성공 사실이고 DebugTrace는 계산 근거다.

Fireball 실행 예시

1. SkillRequest

플레이어가 살아 있는 단일 대상을 지정한다. 요청에는 CommandId, CasterId, SkillId, TargetId, RequestedTick, RootSeed가 들어간다. CommandId는 cast마다 새로 만들고, 나머지 실행 ID와 쿨다운 종료 tick은 이 요청에서 파생한다.

2. Validator

현재 실행 정책은 단일 대상의 생존, 쿨다운, 마나 20 이상을 그 순서로 확인한다. learned와 침묵/기절 같은 control lock 검사는 product 확장이다.

3. Cost & Timeline

목표형 정책에서는 마나 20을 예약하고 release marker에서 비용·쿨다운·Damage 주 효과를 하나의 plan으로 준비한다. 현재 fixture는 예약과 timeline을 축약하고 동등한 plan을 직접 commit한다. 비용의 최종 확정 기준은 commit 성공 receipt다.

4. EffectBundle

DamageEffect가 단일 대상 DamageRequest를 만들고, commit 성공 뒤 ApplyStatusEffect(effect.apply-burn)가 살아 있는 대상에게 Burn 상태를 요청한다.

5. Result

SkillResult는 성공 여부, canonical FailureReason과 실행된 EffectResult 목록만 묶는다. 계산 근거는 DebugTrace, commit된 사실은 outbox event, 후속 Status 적용 결과는 reaction 결과로 각각 분리한다.

안티패턴

스킬이 HP를 직접 수정

SkillExecutor에서 대상 HP를 바로 감소시키면 Effect, Combat, Status, Log가 우회된다. Skill은 EffectBundle만 실행한다.

스킬마다 타겟 검색 직접 구현

각 스킬 코드 안에 범위 검색을 넣으면 사거리, 시야, 팀 필터가 중복된다. TargetingSpec과 TargetSelector로 분리한다.

쿨다운을 UI에만 저장

UI는 표시만 해야 한다. 실제 쿨다운과 charge 상태는 SkillRuntime이 소유해야 저장, 서버 검증, AI 사용이 가능하다.

중단 정책 누락

시전 중 중단 시 비용과 쿨다운 처리가 정해져 있지 않으면 버그가 반복된다. 시점별 환불/쿨다운 정책을 명시한다.

Combat / Status로 이어지는 Handoff

Skill은 Damage를 계산하지 않고 Status를 유지하지 않는다. Skill은 ActionTimeline의 marker에서 EffectBundle을 실행할 뿐이다. EffectBundle 내부의 DamageEffect는 Combat Resolution으로, ApplyStatusEffect는 Status System으로 이어진다.

Comprehension check

이해도 확인

Skill이 조율해야 할 실행 정책과 Effect·Combat·Status에 넘겨야 할 결과 책임을 나눠서 생각한다.

  1. 01 · 책임 경계
    스킬 UI가 실제 쿨다운을 보관하고 SkillExecutor가 release 시 대상 HP를 직접 감소시키는 구조가 왜 잘못됐을까?
    정답과 해설

    실제 쿨다운은 SkillRuntime이 소유하고 UI는 표시만 해야 한다. SkillExecutor는 검증·비용·타임라인을 조율하며 HP 변경은 Effect와 Combat 경로로 위임한다.

  2. 02 · 경계 상황
    목표형 reserve_then_commit 정책에서 release 전 중단, release plan 실패, commit 성공 시 비용은 각각 어떻게 처리해야 할까?
    정답과 해설

    정책상 release 전 중단이면 예약을 취소하고 EffectBundle을 실행하지 않는다. release에 도달했어도 precondition 충돌 등으로 plan commit이 실패하면 비용은 최종 확정되지 않으며 예약을 해제하거나 재시도 정책을 따른다. 비용·쿨다운·주 효과 plan의 commit이 성공한 경우에만 비용이 최종 확정된다. 현재 fixture는 예약과 timeline 자체는 구현하지 않는다.

  3. 03 · 시스템 연결
    목표형 Fireball 조율에서 release 뒤 Burn까지의 handoff 순서는 무엇일까?
    정답과 해설

    Skill과 Effect가 비용·쿨다운·Damage 주 효과 plan을 준비하고 RuntimeCommitter가 한 번에 commit한다. 그 뒤 DamageCommitted를 ReactionQueue 명령으로 바꿔 ApplyStatusEffect → Status 순서로 Burn을 적용한다. 현재 fixture는 release timeline을 축약하지만 commit 이후 handoff는 검증한다.

  4. 04 · 승인 경계
    RequestedTick과 cooldown readyTick이 같고 mana는 충분하다면 승인해야 할까?
    정답과 해설

    승인해야 한다. 계약은 readyTick <= RequestedTick이다. 반대로 readyTick이 한 tick이라도 미래면 Cooldown으로 거부하며, mana도 동시에 부족해도 우선순위상 Cooldown 하나를 반환하고 Combat/RNG는 호출하지 않는다.

설계 점검

  • SkillDefinition이 비용, 쿨다운, 타겟팅, 타임라인, EffectBundle을 모두 데이터로 표현한다.
  • SkillRuntime이 Entity별 배운 레벨, 쿨다운, 차지 같은 장기 availability를 보관하고, SkillExecution이 cast 한 번의 실행 상태를 보관한다.
  • SkillValidator가 상태 이상, 비용, 사거리, 시야, 장비 조건을 검증한다.
  • 목표형 Fireball reserve_then_commit 정책에서는 ActionTimeline의 release marker에서 비용·쿨다운·주 효과 commit plan을 준비한다. 현재 fixture는 timeline·reservation을 구현하지 않으므로 실행 증거와 혼동하지 않는다.
  • 중단 시 비용 환불과 실패 쿨다운 정책이 정의되어 있다.
  • SkillResult가 EffectResult와 canonical 실패 이유를 포함하고, 실행 단계와 실패 근거는 DebugTrace로 연결된다.
  • Fireball 같은 예제가 Skill → Effect → Combat/Status로 끝까지 추적된다.
